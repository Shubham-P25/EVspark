# EVspark (EV Twin) — Codemap

Digital-twin platform for EV charging networks in India. Drivers see live, color-coded stations and a one-tap **Fuel** recommendation (predicted wait, not just distance). Station operators see the same live state plus analytics. Admin governs the network.

**Constraint:** ~1–2 hours to reach ~80%. **Demo priority:** Driver + Station dashboards. Admin and landing polish are the cut line.

## 1. Architecture

```
Twin engine (virtual vehicles + virtual chargers)
   │  OCPP 1.6J frames over WebSocket   (BootNotification, StatusNotification,
   ▼                                      StartTransaction, MeterValues, StopTransaction)
API / CSMS (Express)  ──► Neon Postgres (Prisma)  ── time-stamped events, sessions, rollups
   │  └─► MQTT broker (internal bus, free-tier HiveMQ/EMQX; Mosquitto locally)
   ▼
Socket.io rooms  ──►  Next.js web (Google Maps, shadcn dashboards)
   ▲
FastAPI forecast service  ◄── API calls POST /predict (history + current state)
```

Notes
- Real chargers speak **OCPP-J over WebSocket**, not MQTT. MQTT is the internal bus *inside* our backend. Say this in the report.
- Phase A: twin engine connects to our `/ocpp/1.6/:chargePointId` WebSocket like real hardware would. If behind schedule, publish in-process instead — same event shapes.
- Phase B (optional): swap in open-source virtual charge points (SAP e-mobility-charging-stations-simulator or Solidstudio ocpp-virtual-charge-point). The CSMS needs no changes.
- All simulated rows carry `source = 'sim'`; the UI shows a small "Simulated live data" badge. Honest and defensible.

## 3. Data plan

**L1 — Stations (real, all India)**
- Ministry of Power station-level dataset (via Dataful, dataset 23369): operator, state, district, city, location name, lat, lng, charger type, charger rating, connector rating, total connectors. Data-as-of 26-10-2025. May need login/download.
- Enrich with Open Charge Map API (free key) for amenities/extra connectors.
- Import all India; **simulate live traffic on ~50–100 stations** in Mumbai / Thane / Navi Mumbai / Pune.
- No live status/price/reviews in official data → generated by twin + seed.

**L2 — Analytics patterns (real session data, remapped to India)**
- ACN-Data (Caltech/JPL): 30k+ sessions with arrival, departure, energy.
- Dundee city open data: sessions, charger power; rapid-charger avg ≈ 28 min.
- UrbanEV (Shenzhen, Dryad doi:10.5061/dryad.np5hqc04z): hourly occupancy, duration, volume, price, 20k+ stations, 6 months.
- Method: learn hourly demand curve, weekday factor, session duration and energy distributions → apply to Indian stations. **State this explicitly in the report.**
- Optional Indian energy context: Telangana EV charging electricity-consumption datasets (monthly).

**L3 — Live data:** twin engine (Section 8).

**L4 — Camera/sensors:** later. Mock panel fed by `occupancy_count`, `temperature`, `power_kw` from the simulator.

**Vehicle models:** build a `vehicle_models` table (Indian EVs: Nexon EV, Tigor EV, MG ZS/Windsor, Creta EV, Ather, Ola S1, etc.) with battery kWh, max AC/DC kW, connector types. iReV (github.com/ikppramesh/iReV) lists 40+ Indian models — reference only, check its license before copying.

## 6. Wait-time and recommendation logic (put in `packages/shared`, unit-test it)

**Current wait at a station for a given connector**
1. Compatible chargers = same connector, not faulted/maintenance.
2. For each busy charger: `remaining = max(0, expected_end − now)`, where expected_end comes from session start, SoC and kW (updated by MeterValues).
3. Free compatible charger exists → `wait = 0`.
4. Otherwise, greedily assign the queued vehicles ahead of you, in order, to the earliest-free charger (each adds that charger's average session length). Your wait is the time your turn begins.

**Geolocation approach (same pipeline for demo and real users)**
- A station geofence of ~100–150 m. Users inside the geofence who are *not* charging count as `queue_geo`. Demo vehicles send the same GPS pings as real app clients, so nothing changes when real users arrive.
- Final queue estimate = max/blend of `queue_ocpp` and `queue_geo`.

**Forecast:** FastAPI `POST /predict` with station history + current state → `{predicted_wait, confidence}` for +30 min. Fallback if the model isn't ready: moving average of the same hour-of-week from `station_metrics_hourly`. Log predictions into `forecasts` and fill `actual_wait` later (for the accuracy metric in the report).

**Fuel score (lower is better)** at the driver's *arrival time* (ETA), not now:
`score = w1·drive_min + w2·predicted_wait_at_ETA + w3·price_penalty + w4·(5 − rating)`
Default weights 1.0 / 1.2 / 0.3 / 0.5. Filter by connector, vehicle max kW and range reachability first. Return top 3 plus reasoning ("6 min wait, 1.8 km").

**Marker color:** green wait ≤ 5 min · yellow 5–15 · red > 15, or all compatible chargers busy and queue ≥ 3. Faulted/maintenance chargers are excluded from the available count.

**Overload alert:** when a station crosses its threshold → `alert:overload` to the operator room, red highlight on the charger/station card, and a hint to the driver-side recommender to deprioritize it (this is the "reroute" story).

## 8. Twin engine spec (`scripts/twin-engine`)

- **Time:** `SIM_SPEED` (default 10×), deterministic `SIM_SEED`, tick every 1 s real time.
- **Arrivals:** per station, Poisson process with `λ_s(t) = base_s × hourly_curve(h) × weekday_factor × surge_s`. `base_s` from number of chargers × kW × location type (highway/mall/residential). Hourly curve and weekday factor learned from UrbanEV/ACN/Dundee.
- **Vehicle:** model (from `vehicle_models`), connector, battery kWh, `soc_now` ~ U(10, 60)%, `soc_target` ~ U(80, 100)%.
- **Station choice:** 60% nearest compatible · 25% follow the Fuel recommendation · 15% cheapest within radius.
- **Movement:** vehicles spawn ~3–10 km away, move along a Directions polyline (straight-line interpolation as fallback), emit GPS pings every few seconds, and enter the geofence on arrival.
- **Charging:** free compatible charger → `StartTransaction`. Duration = `(target − now) × battery_kWh / (min(charger_kW, vehicle_max_kW) × 0.85)` → roughly 10–60 min. `MeterValues` every 30 sim-seconds, `StopTransaction` at the end, ₹ amount = kWh × station price.
- **Queueing:** if all compatible chargers are busy the car waits; patience ~ N(12, 4) min then abandons (and may try another station).
- **Faults:** ~0.5%/charger/hour, repair 10–60 min → `StatusNotification Faulted`.
- **Controls:** admin slider for speed; **surge mode** forces chosen stations toward red; pin 2–3 "hero" stations (one free, one crowded, one faulted) so the demo story is always visible.

## 10. Industrial-grade checklist

**Backend**
- TypeScript strict everywhere; zod validation on every request and every OCPP frame.
- Server-side RBAC middleware per route; ownership checks (operators only touch their own stations).
- `helmet`, CORS allowlist, `express-rate-limit`, request size limits.
- Structured logging (pino) with request IDs; central error handler; consistent error JSON.
- Prisma migrations only (no manual schema edits); idempotent, seeded (`SIM_SEED`) scripts.
- Append-only `charger_events` + hourly rollup via node-cron; retention policy for old raw events.
- `/healthz`, `/readyz`; graceful shutdown for ws/mqtt/db.
- Unit tests for wait-time, scoring, arrival model; one integration test for recommend + OCPP flow.

**Frontend**
- Loading, empty, and error states on every data view; skeletons for map panels.
- Marker clustering for large station counts; debounce map-bounds queries.
- Accessible: contrast, 44px touch targets, keyboard focus, aria labels on map controls.
- Env-validated config; Google key restricted by HTTP referrer + API list (separate server key IP-restricted).

**Ops**
- `.env.example`, no secrets in git; GitHub Actions: lint + typecheck + tests.
- `docker-compose.yml` for local MQTT + API; README with architecture diagram and "how data is simulated" section.
- Admin system-health panel: MQTT, ML latency, active sockets, simulator state.

**Report/credibility**
- Document data provenance (L1 official dataset, L2 remapped real sessions, simulated live traffic) and the forecast accuracy metric (predicted vs actual wait, MAE/RMSE).
